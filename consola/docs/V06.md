# Consola v0.6

## Abrir y configurar

Desde la raíz, con las dependencias existentes:

```powershell
.\.venv\Scripts\python.exe scraper/run.py serve
```

Abrir [Inicio](http://127.0.0.1:8000/v0.6/). Si el proceso se inició antes de este cambio, reiniciarlo. La ruta del catálogo continúa siendo `/v0.4/`; la interfaz técnica `/` se conserva. No se hizo despliegue a producción.

Variables opcionales para el proceso web **y** el scraper si se quiere evaluar después de sus ejecuciones:

| Variable | Uso |
| --- | --- |
| `METRO_DB` | Catálogo existente, de solo lectura para la consola |
| `RADAR_CRM_DB` | SQLite auxiliar; por defecto `metro-consola.sqlite` junto al catálogo; debe ser distinta |
| `GEMINI_API_KEY` | Clave del proveedor; nunca guardarla en Git ni en formularios |
| `GEMINI_MODEL` | ID Gemini Flash disponible para la cuenta; valor predeterminado `gemini-3.8-flash` |
| `GEMINI_MAX_CANDIDATES` | Candidatos relevantes por oportunidad y cálculo, 1–30; predeterminado 20 |

El modelo predeterminado y el nivel de razonamiento bajo siguen la [guía oficial de Gemini 3.8 Flash](https://ai.google.dev/gemini-api/docs/whats-new-gemini-3.8). No se envían parámetros de muestreo obsoletos.

No se carga `.env` automáticamente. Definir variables en el entorno antes de iniciar. Un modelo ausente o inválido genera feedback y deja disponible el matching determinista. Revisar disponibilidad del modelo y facturación en la cuenta antes de habilitarlo. El objetivo inferior a US$10 al mes necesita medir tokens, frecuencia de actualizaciones y futuro alojamiento. El límite de candidatos y caché reducen llamadas, pero no constituyen un tope de gasto del proveedor.

Guardar fuentes solo persiste configuración. Para usarlas en una ejecución futura explícita:

```powershell
.\.venv\Scripts\python.exe scraper/run.py scrape --fuentes-registradas
```

Se pueden combinar con `--url` explícitas y se deduplican. Sin esa opción el scraper conserva su selección anterior. `--resume` conserva las fuentes de la ejecución reanudada. Una extracción completada recalcula las oportunidades abiertas de clientes activos, sin escribir nada del CRM en el catálogo.

## Funcionamiento

- Dashboard: exactamente cuatro secciones; no hay quinta sección de actividad.
- Clientes: Activos/Inactivos independientes del estado abierta/cerrada de la oportunidad. Cada entidad conserva sus IDs, fechas y relaciones.
- Formulario: barrios alternativos, presupuesto mínimo opcional/máximo obligatorio y rango opcional de habitaciones. Área, baños, parqueaderos, antigüedad y texto son preferencias. No hay controles para cambiar manualmente la obligatoriedad de cada campo.
- Selector de barrios: primero se elige la ciudad. Si hay una sola ciudad, se preselecciona. El buscador distingue entre ciudad pendiente de elegir, ciudad sin barrios disponibles y texto sin coincidencias; no muestra una lista vacía sin explicación. Los barrios provienen del catálogo, no de todas las ubicaciones posibles de la ciudad. Cuando faltan, se pueden escribir en las características adicionales existentes.
- Matching: conserva desconocidos como pendientes, descarta incumplimientos estrictos conocidos. Los datos de baños siempre están disponibles en los candidatos cuando existen.
- IA: JSON estructurado, validación, evidencias, caché y lote acotado. Una fila sin evaluación vigente lo indica; no se fabrican explicaciones. Orden por IA disponible sin alterar la condición estricta del candidato.
- Decisiones: persistentes por oportunidad/inmueble; se pueden cambiar y revisar aunque desaparezcan de los candidatos. No envían comunicaciones.
- Catálogo: mismos filtros, historial, comentarios, búsquedas de origen y CSV de v0.5. La navegación al catálogo recuerda filtros y página en el navegador.

## Pruebas

Las pruebas usan bases sintéticas y no llaman al proveedor. Desde la raíz:

```powershell
foreach ($radarSuite in @('consola', 'catalogo', 'scraper')) {
    .\.venv\Scripts\python.exe -c "import sys,pathlib; r=pathlib.Path.cwd(); sys.path[:0]=[str(r),str(r/'scraper'),str(r/'consola/tests')]; import pytest; raise SystemExit(pytest.main(['--rootdir=.','-o','pythonpath=',sys.argv[1]+'/tests','-q','--basetemp=.tmp/pytest-v06-'+sys.argv[1]]))" $radarSuite
    if ($LASTEXITCODE -ne 0) { throw "Falló la suite $radarSuite" }
}
```

Cada suite corre en un proceso separado para que el loop de Playwright no interfiera con las pruebas que usan `asyncio.run`. La inclusión explícita de rutas evita la ambigüedad de los tres `pytest.ini`. En Windows, TestClient y Chromium necesitan permitir sockets locales al ejecutor. La prueba v0.6 verifica 1440×900, 768×1024 y 390×844, crea capturas en `.tmp/`, comprueba ausencia de desbordamiento de página y recorre alta, revisión y regreso al catálogo filtrado.

### Corrección posterior: registro y selector de barrios

El acceso «Registrar cliente y necesidad» abre `/v0.6/nuevo`, el formulario de registro; su título ahora coincide con el botón. Con varias ciudades, antes se podía abrir el selector sin elegir ciudad y aparecía un mensaje genérico de búsqueda sin resultados. La corrección indica el paso pendiente, deshabilita la búsqueda hasta contar con barrios de esa ciudad y distingue entre ciudad sin barrios disponibles y texto sin coincidencias. Con una sola ciudad preseleccionada, los barrios se muestran inmediatamente.

Se añadieron pruebas de regresión en escritorio y móvil para ese patrón de datos, selección por teclado, búsqueda por tildes, guardado completo y ciudad única. La comprobación del caso real fue de solo lectura, sin guardar formularios ni alterar el catálogo. No se añadieron barrios artificiales ni se modificó el matching.
